# Программная архитектура v0.2 (бумажный дизайн, до железа)

Сначала работает на dev-станции CM5 (D11), позже на полевом носителе. Linux (база Raspberry Pi OS), все сервисы в user-space, управление через systemd.

## Канал управления (решено D12: Wi-Fi AP)

У узла по дизайну нет радио; канал к телефону живёт на MVP сетевом модуле. Варианты были:

| Вариант | Железо | Плюсы | Минусы |
|---------|--------|-------|--------|
| A. Wi-Fi AP на сетевом модуле (ESP32/USB-WiFi на H2) | единственный сетевой модуль MVP становится точкой доступа | без проводов, телефон остаётся на мобильном интернете | Wi-Fi рядом с LoRa/GPS; выбор модуля привязан к Wi-Fi |
| B. USB-C кабель телефон↔узел (tethering) | ничего лишнего | ноль RF, максимальная надёжность | только кабель; согласование ролей/PD USB-C мудрёное |
| C. BLE через ESP32-компаньона | ESP32 в слоте Class L | малое потребление, современное сопряжение | низкая пропускная BLE; лишний модуль |

Решение (D12): **A — Wi-Fi AP на MVP сетевом модуле** (трафик управления остаётся в сети узла; мобильный интернет телефона не трогаем). USB-C tethering задокументирован как запасной.

## Сервисы узла (systemd-юниты)

| Сервис | Обязанность |
|--------|-------------|
| ofn-powerd | Читает INA219, исполняет политику питания (отсечка: USB-A → слоты → ядро никогда), low-power режим при питании от USB-C |
| ofn-slotd | Опрос слотов: чтение ID EEPROM (формат Pi HAT), применение лимитов тока из дескриптора, слоты ручной конфигурации из /etc/ofn/slots.conf, I2C-подсказки для готовых модулей |
| ofn-modmgr | Жизненный цикл модулей: привязка драйверов по классу, реестр модулей наружу через control API |
| ofn-mission | Исполнение задач: расписания, LoRa/Meshtastic сессии, задания захвата |
| ofn-logd | Локальные логи + управление хранилищем + кольцевые буферы |
| ofn-syncd | Store-and-forward: при подключении телефона синхронизирует логи и результаты миссий |
| ofn-ctl-api | Точка входа Control API (ниже) — единственная дверь для Android-приложения |

Состояние в /var/lib/ofn (файлы + sqlite). Конфигурация в /etc/ofn. Нигде нет зависимости от облака.

## Control API

- Транспорт: WebSocket поверх канала управления (вариант A: на AP узла, 10.0.0.1:8443, TLS с пиннингом сертификата из Android-приложения).
- Протокол: JSON-сообщения, запрос/ответ + события (горячее подключение модуля, события питания, прогресс миссии).
- Аутентификация: код сопряжения через паттерн мигания LED / вывод при первом старте; приложение хранит идентичность узла. Никаких аккаунтов и внешних сервисов.
- Область: список/управление модулями, запуск/стоп/статус миссий, live телеметрия (INA219/слоты), выгрузка логов, режим питания, обновления прошивки/конфига.
- Функции security lab работают только против целей, помеченных как собственные в конфиге миссии (правило безопасности проекта).

## Android-приложение (компаньон)

- Kotlin, подключается по каналу управления, offline-first: планирует миссии, потом синхронизирует.
- Экраны: Дашборд (питание/телеметрия), Модули, Миссии, Логи, Настройки.
- Приложение — это и есть дисплей, которого у устройства нет: всё планирование миссий на телефоне.

## Survival mode

- Триггер сейчас (без батареи): телефон отключён, питание в норме → узел сам выполняет запланированные миссии и пишет локально.
- С батареей (пост-MVP gate): пропадание входа → ofn-powerd переходит на батарейный профиль, отсекает выходы зарядки, отсекает слоты по приоритету миссий, ядро троттлится.

## Структура репозитория (план)

```
open-field-node/
  docs/            (этот дизайн-пакет)
  ofn-node/        (сервисы, Rust или Go — выбрать на первом кодовом этапе)
  ofn-android/     (приложение-компаньон)
  ofn-fw/          (прошивки модулей, если на модулях MCU)
  ofn-eep/         (шаблоны дескрипторов + eepmake-исходники)
```
